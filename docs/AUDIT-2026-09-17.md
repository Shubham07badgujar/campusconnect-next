# CampusConnect — Repository Audit

**Audited revision:** `4dc4140` on `main` (in sync with origin, clean working tree)
**Date:** 2026-09-17
**Scope:** full repository — 185 TS/TSX files, ~44,800 lines, 56 API routes, 28 Firestore collections
**Method:** direct source reading and command-line verification. Every claim below was checked against the working tree at the revision above. Where a widely-held assumption turned out to be **false**, it is called out explicitly.

> **No code was changed in the course of this audit.** Two untracked artefacts (`Campus-Connect-Complete-Client-User-Manual.docx` / `.pdf`, ~17 MB combined) sit in the repo root; they are not committed but are also not gitignored.

---

## 0. Corrections to previously-stated assumptions

Three claims that have been repeated (including in the earlier expansion plan) are **not true**. Recording them so nobody spends effort on a non-problem.

| Claim | Verdict | Evidence |
|---|---|---|
| "Teacher IDs cap at 99 and onboarding stops" | **FALSE** | `users.ts:188` uses `padStart(2, "0")`, which is a *minimum* width, not a fixed one. Verified empirically: `maxSequence 99 → PM100 → PM101 → … → PM999`. No regex, `slice(2)`, or fixed-width parse exists anywhere in `src/`. Parse-back via `parseInt(candidateId.slice(prefix.length))` is width-agnostic. |
| "Mixed-width IDs will break sorting" | **FALSE in practice** | Lexicographic sort *would* misorder (`PM100` < `PM99`), but nothing sorts by teacher ID. `teachermanagement/page.tsx:372-377` sorts by department then name, and no Firestore query uses `orderBy` on a teacher ID. |
| "`resolve-login` leaks teachers' personal email addresses" | **OVERSTATED** | `resolve-login/[loginId]/route.ts:32-37` prefers `authEmail` **first** (`pm01@campusconnect.teacher`), which is derivable from the login ID itself. It falls back to the personal `email`/`contactEmail` only when `authEmail` is absent. The real issue is unauthenticated **enumeration**, not PII disclosure. |

The teacher-ID code *does* have serious defects — they are a race condition and a full-collection scan, documented in §1.2. The severity was misattributed, not invented.

## 1. Confirmed issues

Ordered by severity.

### 1.1 — CRITICAL: the realtime socket is unauthenticated and writes with the Admin SDK

This is the single most serious finding. It is exploitable today, in the current single-college deployment.

**There is no authentication on the socket at all.** `grep -n "io.use"` across `server.ts`, `src/server/socket.ts`, `src/lib/server/socket-io.ts` returns **zero matches**. Identity is read from a client-supplied query string:

```ts
// src/server/socket.ts:59 and :134
const connectedUserId = String(socket.handshake?.query?.userId || "").trim();
```

The `send_message` handler destructures the sender's identity **from the message payload**:

```ts
// src/server/socket.ts:156-167
socket.on("send_message", async (messageData) => {
  const { chatId, message, senderId, receiverId, timestamp, attachment, replyTo } = messageData as {...};
```

…validates only that the fields are non-empty (`socket.ts:174`), and writes them unmodified using the **Admin SDK**:

```ts
// src/server/socket.ts:217-226
const messageRef = await adminApp.firestore().collection("messages").add({
  chatId, message: normalizedMessage, attachment: normalizedAttachment,
  replyTo: normalizedReplyTo, senderId, receiverId, timestamp: normalizedTimestamp, read: false,
});
// src/server/socket.ts:234-238
await adminApp.firestore().collection("chats").doc(chatId).update({ ... });
```

**The Admin SDK bypasses `firestore.rules` by design.** So the carefully-written chat rules — `senderId == request.auth.uid` (`firestore.rules:114`), `isChatParticipant(...)` (`:115`), the `onlyChanges([...])` restriction (`:107`) — are **never consulted on this path**.

Compounding it, the socket accepts cross-origin connections:

```ts
// server.ts:30-33
const io = new Server(httpServer, {
  // Same-origin in production; loose CORS keeps localhost dev tooling happy.
  cors: { origin: true, credentials: true },
});
```

The comment is factually wrong: `origin: true` **reflects any origin**, in production as well as development.

**What an attacker can do with no account and no token:**
1. Forge a persisted chat message from any user to any user (`join_chat` at `socket.ts:24` joins any room id with no membership check).
2. Overwrite any chat thread's `lastMessage` metadata on an arbitrary `chatId`.
3. Eavesdrop on live conversations via `receive_message`/`typing_indicator` broadcasts.
4. Spoof attendance presence: connect as `?userId=<victim uid>` and emit `join_attendance_session` with attacker-chosen GPS. The role check at `socket.ts:71-73` validates the *claimed* user's stored role, not the connection's identity — so it stops teacher impersonation in the heatmap but not student impersonation.

Note also that chat has **two authorization regimes for the same user action**: `Chats.tsx:1244-1259` emits over the socket when connected (Admin SDK, no rules) and falls back to `addDoc` otherwise (rules enforced).

### 1.2 — CRITICAL: teacher-ID race causes account takeover

The real defect, correctly characterised. `generateTeacherId` (`src/lib/server/users.ts:157-190`) reads the entire `teachers` collection, computes `max + 1`, and is **not inside a transaction** (confirmed: no `runTransaction` in the teacher path).

Two concurrent `POST /api/teachers` for the same job profile both derive the same ID. Then in `src/app/api/teachers/route.ts:97-123`, request B's `getUserByEmail("pm05@campusconnect.teacher")` **succeeds**, so B takes the `updateUser` branch — **resetting teacher A's password, renaming A's account, and overwriting `teachers/{A.uid}` with B's details.** Teacher A is silently taken over.

**This is also reachable without concurrency.** Teacher deletion is client-side and removes only the Firestore document:

```ts
// src/app/(admin)/admin/teachermanagement/page.tsx:350-356
const docRef = doc(firestore, "teachers", id);
await deleteDoc(docRef);
```

`/api/users/delete` — the only endpoint that removes an Auth user — is never called here. The Firebase Auth account survives, `maxSequence` drops back, the next hire is issued the same ID, and inherits the deleted teacher's UID and auth record. Orphaned `teacherStudentMappings` rows survive too.

Secondary: `PUT /api/teachers/[uid]:99-100` drops the `previousProfile &&` truthiness check present in the POST version, so a teacher with a blank/unrecognised `jobProfile` gets a **new ID and new login email on every save**.

### 1.3 — CRITICAL: students created via the admin UI can never be marked present

`POST /api/users` — the "Add Student" path — writes **only** to `users` (lines 31, 37, 83). It never writes the `students` document, never writes `prn`, and **never writes `subjects`**.

Attendance membership requires a subject match:

```ts
// src/lib/server/attendance/shared.ts:108-110
return studentSubjects.some((subject) =>
  subjectMatches(sessionData?.subjectName || "", sessionData?.subjectId || "", subject),
);
```

`.some()` on an empty array is `false`. **Every student added through the admin UI is therefore invisible to every attendance session, permanently.** Only the bulk-onboarding path (`bulk-onboard-students/route.ts:185-209`, which writes `subjects` and both documents) produces working students.

### 1.4 — HIGH: `users` is world-readable and mirrors all student PII

`firestore.rules:59` — `match /users/{uid} { allow read: if isSignedIn(); }`

`firestore.rules:71` correctly restricts `students/{uid}` to `isStaff() || isSelf(uid)`. But `bulk-onboard-students/route.ts:202-209` writes **the identical payload to both collections**:

```ts
const studentPayload = { uid, name, email: authEmail, loginId: prn, prn, rollNo: prn,
  rollNumber: prn, phone, mobile: phone, dept: branch, department: branch,
  year, semester, subjects, role: "Student", contactEmail, ... };
await firestore.collection("users").doc(userRecord.uid).set(studentPayload);
await firestore.collection("students").doc(userRecord.uid).set(studentPayload, { merge: true });
```

**The privacy control on `students` is nullified by the mirror in `users`.** Any single student account can read the entire student body's name, PRN, **phone number**, personal email, department, year and semester.

`teachers/{uid}` is likewise `allow read: if isSignedIn()` (`:77`) and contains every teacher's `mobile`, `contactEmail`, and `loginId`/`authEmail`.

### 1.5 — HIGH: attendance rollup is fire-and-forget and can silently corrupt percentages

```ts
// src/app/api/attendance/end/route.ts:176-179 … 217-221
void (async () => {
  for (const studentId of enrolledStudentIds) { ... await attendanceRef.set(...) }
})().catch((error) => { console.error("Deferred attendance rollup failed:", error); });

return NextResponse.json( ... );   // returns 200 before the rollup finishes
```

The endpoint returns success **before** the per-student counters are written. A failure — or an instance restart, which the free hosting tier makes routine — at student 30 of 60 leaves half the class's `student_attendance` counters incremented and half not. There is no reconciliation path and no error surfaced to anyone.

### 1.6 — HIGH: a missing index degrades into a silent institution-wide table scan

```ts
// src/lib/server/attendance/shared.ts:166-169
    return await queryRef.get();
  } catch {
    return null;
  }
```

A `FAILED_PRECONDITION: The query requires an index` is swallowed to `null`, filtered out at `:173`, making `merged.size === 0` true at `:183`, which triggers the full-collection fallback at `:184-190` (`users where role=="Student"` + all of `students`). **A missing index produces no error — it produces a permanent silent full scan on every attendance session start.**

### 1.7 — HIGH: batch writes exceed Firestore's 500-operation limit

Unchunked batches that fail on real data volumes:

- `save-exam-timetable/route.ts:88-102` — one `batch.set` per parsed exam row, caller-supplied, validated only for `length === 0`. A full institution schedule (6 branches × 4 years) clears 500 easily.
- `clear-exam-timetable/route.ts:33-38` — with `clearAll`, one unchunked delete of the entire collection.
- `academic-calendar/page.tsx:527-531` — `handleBulkDeleteAll`; the confirm dialog at `:519-521` prints the count, so the user is told it's 900 and it still fails.
- Also `academic-calendar/page.tsx:494-500`, `:788-831`, `:856-898`; `admin/exam-timetable/page.tsx:953-957`; `save-exam-timetable:36-47`; `upload-exam-timetable-pdf:72-83`; `upload-academic-calendar-pdf:71-82`.

Correctly chunked, for contrast: `users.ts:314-338` (400), `attendance/session/[id]:246-255` (400), `remove-duplicate-exams:47-58` (500, zero headroom).

### 1.8 — MEDIUM: bulk academic update is destructive, non-atomic, and partly a no-op

```ts
// src/app/api/admin/bulk-update-student-academics/route.ts:105-127
const academicUpdatePayload = { year, semester, dept: branch, department: branch,
  subjects, updatedAt: new Date().toISOString(), onboardingSource: "bulk_academic_update" };
await firestore.collection("users").doc(...).set(academicUpdatePayload, { merge: true });
await firestore.collection("students").doc(...).set(academicUpdatePayload, { merge: true });
```

- **Destructive:** `{merge: true}` merges per field, so `year`, `semester`, `dept`/`department` and the **entire `subjects` array** are replaced wholesale. No prior values are captured anywhere.
- **Non-atomic:** a plain `for` loop (`:36`) issuing 2 reads + 2 writes per student sequentially — 2,000 round trips for 500 students. A failure between the `users` write (`:117`) and the `students` write (`:122`) leaves that student at different years in the two collections, which different call sites resolve differently (`utils.ts:64-82` spreads `users` over `students`; `teacher-students/page.tsx:120-127` absorbs `students` first).
- **Silent no-op:** `:81-86` prefers the *input* for year/semester but the *stored value* for branch, so the bulk-branch control in `bulk-academic-update/page.tsx:158-165` does nothing for any student who already has a `dept` — i.e. all of them. The admin sees a green success summary.
- Nothing re-syncs `teacherStudentMappings`, `attendance_sessions.enrolledStudentIds`, or existing `student_attendance` rows after a promotion.

### 1.9 — MEDIUM: subject renames orphan all history

`makeSubjectId` derives the key from the subject **name**:

```ts
// src/lib/server/attendance/shared.ts:14-20
export const makeSubjectId = (subjectName: unknown = ""): string =>
  String(subjectName || "").trim().toLowerCase()
    .replace(/[^a-z0-9]+/g, "_").replace(/^_+|_+$/g, "");
```

It is embedded in the document IDs of `student_attendance` (`{studentId}_{subjectId}`, `attendance/end:180`) and `subject_attendance_stats` (`{subjectId}_{teacherId}`, `:200`). Renaming a subject through `PUT /api/admin/subject-sets` rewrites only the `subjects` array and cascades nowhere, causing five distinct breakages: orphaned attendance history, stale `timetables` rows that can no longer be edited, teacher authorization flipping to 403 on both old and new IDs, empty student rosters, and collisions (`CAD/CAM`, `CAD-CAM`, `CAD CAM` all collapse to `cad_cam`).

It is also **re-implemented, non-identically**, at `student-dashboard/page.tsx:56-60` (missing the `.trim()`), and inlined again at `teacher-attendance/page.tsx:922-924`, `:1138-1141`.

### 1.10 — MEDIUM: no rate limiting anywhere except the OTP flow

`grep -rn "rateLimit|rate-limit|ratelimit|throttle|helmet"` → zero matches outside OTP. The only throttles are a 45-second per-account cooldown (`password-otp/request/route.ts:52-65`) and a 5-attempt OTP limit (`verify/route.ts:67-96`). **There is no per-IP limit anywhere**, including on `POST /api/auth/password-otp/request`, which is unauthenticated and both writes Firestore and sends mail.

### 1.11 — MEDIUM: role enforcement is split-brained between rules and guards

`auth-guards.ts` accepts **Firestore-document** roles as a fallback:

```ts
// auth-guards.ts:87-94 (admin via document), :107-115 (teacher), :162-166 (student)
const adminDoc = await adminApp.firestore().collection("admins").doc(decodedToken.uid).get();
if (!adminDoc.exists) { return fail(403, "Only admins are authorized"); }
```

`firestore.rules` accepts **only claims** (`:30`, `:34`). So an account with an `admins/{uid}` document but no claim is a full admin through `/api/admin/*` yet denied in the browser — and the admin UI mixes both paths. Worse, enforcement is inconsistent *within* the API: `attendance/student/[studentId]/route.ts:31-40` authorizes on claims only, so the same account gets 200 on `/api/users` and 403 there.

Related: all three `setCustomUserClaims(uid, { teacher: true })` calls (`teachers/route.ts:125`, `teachers/set-role:22`, `teachers/[uid]:144`) pass an **object literal, not a merge** — setting the teacher claim on a user who also held `admin: true` silently erases the admin claim.

### 1.12 — MEDIUM: other confirmed issues

- **No security headers.** `next.config.ts` (read in full) has no `headers()` function — no CSP, HSTS, `X-Frame-Options`, `X-Content-Type-Options`, or `Referrer-Policy`. No `middleware.ts` exists.
- **Upload MIME allowlisting trusts the browser.** `file-text.ts:56-61` checks `file.mimetype` — the client-declared Content-Type — and has a `.csv`-extension escape hatch that bypasses the type check entirely. No magic-byte sniffing. (Size limits *are* enforced: 10 MB, `cloudinary.ts:19`, in all upload routes; and Cloudinary deletion is correctly prefix-locked at `cloudinary.ts:39-45`.)
- **Hardcoded OTP pepper fallback.** `constants.ts:309-311` — `process.env.PASSWORD_RESET_OTP_SECRET || "campusconnect-password-reset"`. If the env var is unset, OTP and reset-token hashes are peppered with a value published in the source tree.
- **Credentials emailed in plaintext.** `api/users/route.ts:97-101`, `bulk-onboard-students:216`.
- **Teacher self-profile edit is denied by the rules.** `edit-profile/page.tsx:252` writes `teachers/{uid}` from the browser, but `firestore.rules:78` is `allow write: if isAdmin()`. A live functional/rules mismatch.
- **Legacy path rewrites double the API surface.** `next.config.ts:13-21` exposes `/attendance/:path*`, `/timetable/:path*`, `/verify-admin` as unprefixed aliases. Guards still apply (same handlers), so this is surface duplication and cleanup debt rather than an auth bypass.
- **`firestore.rules:15` contradicts itself** — the header comment lists `subjectSets` as "NOT exposed to clients", while `:209-212` grants `allow read: if isSignedIn()`.
- **15 known dependency vulnerabilities** (3 high, 9 moderate, 3 low) via `npm audit`. The load-bearing one is **`nodemailer` (high): "Email to an unintended domain can occur due to Interpretation Conflict"** — this application emails student credentials through nodemailer. Also `node-fetch` (high) and `postcss` (high, build-time).

## 2. Already-fixed / verified-correct

Credit where due — these are genuinely right, and should not be "fixed".

- **Secrets hygiene is clean.** `service-account-key.json` and `.env.local` exist on disk but are **untracked**; `.gitignore` covers `.env.*`, `service-account-key.json`, and `rotated-credentials-*.csv`; `git log -S"BEGIN PRIVATE KEY"` returns nothing — **no secret has ever been committed.** `.env.example` is present and explicitly un-ignored.
- **Default-deny rules.** `firestore.rules:215-217` — `match /{document=**} { allow read, write: if false; }`. This correctly locks all 12 server-only collections (attendance, biometrics, OTP, mappings). Verified: zero browser code touches any of them.
- **Guard coverage is high and correctly applied.** 48 of 56 route files (51 of 59 handlers) call a guard, and **every one enforces the result** — no route imports a guard and forgets to apply it. The 8 unguarded routes are the 3 OTP endpoints, `verify-admin`, `health`, `keep-alive`, `subjects`, and `resolve-login`.
- **Guards distinguish 401 from 503** (commit `2d997d2`) — `auth-guards.ts:46-50, 71`. A fail-closed improvement; no guard was weakened.
- **Passwords are CSPRNG-generated server-side** (`passwords.ts:7-13`, `crypto.randomInt`) and client-supplied passwords are explicitly ignored (`api/users/route.ts:15-16`).
- **Attendance duplicate-marking is guarded** (`attendance/mark:244-256`).
- **Field-level self-edit restrictions work.** `firestore.rules:62-66` blocks self-writes to `role, prn, rollNo, rollNumber, subjects, year, semester, dept, department, loginId, email, uid`.
- **Chat and message rules are correct** — participant checks, `senderId == request.auth.uid` on create. (They are simply bypassed by the socket; see §1.1.)
- **No XSS sinks** — zero `dangerouslySetInnerHTML` or `eval(` in `src/`.
- **Filename sanitisation** on chat uploads (`upload-chat-attachment:44-46`).
- **Three batch paths are correctly chunked** (§1.7).
- **The build and typecheck both pass** at this revision (`npm run build` → success; `tsc --noEmit` → exit 0, zero errors).

## 5. Security vulnerabilities

Summarised from §1: unauthenticated socket with Admin-SDK writes (§1.1), world-readable `users`/`teachers` PII (§1.4), teacher-ID race → account takeover (§1.2), no rate limiting (§1.10), rules-vs-guards split-brain (§1.11), no security headers, browser-trusted upload MIME, hardcoded OTP pepper fallback, plaintext credential emails, unauthenticated teacher-ID enumeration via `resolve-login`, and 3 high-severity dependency CVEs including `nodemailer`.

---

## 6. Data-model weaknesses

- **No term / academic-year entity anywhere.** `year` is a study-year string (`"1st".."4th"`), `semester` is `"1"|"2"`; both are plain profile fields. The only calendar-year label in the system is free text on an uploaded PDF (`academicYear`, defaulting to `"General"`). Consequence: `student_attendance/{studentId}_{subjectId}` is a **single lifetime counter** spanning every term the student ever took the subject — so the per-semester 75% rule cannot be computed, and promotion destroys the prior term (§1.8).
- **No enrollment join.** `enrollments` is read but never written. Real membership is inferred by field matching (`shared.ts:83-111`) over a 2×2 collection/alias grid with a full-scan fallback.
- **No subject entity.** Subjects are bare strings; the ID is derived from the name (§1.9).
- **Duplicate storage.** Every student is written twice, non-atomically, to `users` and `students` — and `/api/users` writes only one of them (§1.3).
- **Four aliases for one identifier** (`prn`/`rollNo`/`rollNumber`/`loginId`), two for branch (`dept`/`department`), two for phone, three for name, two for teacher ID, four for email. `shared.ts:251-259` brute-forces a 2×3 matrix to resolve one student.
- **No uniqueness constraint on PRN.** Three partial layers exist (in-file set, in-memory index from a full scan, Firebase Auth email collision); two concurrent bulk uploads both pass.
- **No audit trail.** Confirmed: zero occurrences of `auditLog`/`audit_log`/`activityLog`/`auditTrail` in `src/`. **21 hard-delete call sites, 0 soft-delete markers.**

## 7. Scalability problems

- **No pagination anywhere.** `grep "startAfter|startAt|endBefore"` → **zero hits** repo-wide. Fixed `limit()` caps exist on 8 client listeners, none able to fetch page 2.
- **Unbounded server reads** on hot paths: `users.ts:168` (every teacher save), `users.ts:216-217`, `onboarding.ts:200-201` (every bulk operation), `shared.ts:185-186` (silent fallback, §1.6), `subject-sets.ts:15` and `:53` (**scans twice per call**), `exam-reminders.ts:45`/`:156`, `save-exam-timetable:52`, `attendance/sessions/active:17-19` (institution-wide, then filtered in JS).
- **Worst client offender** — `teacher-dashboard/page.tsx:172-200` downloads **every timetable row for the entire institution, serially across two collection names**, and discards ~99% in JavaScript, on every dashboard load — even though `GET /api/attendance/teacher/lectures` already does the `where("teacherId","==")` server-side. `firestore.rules:192` permits it.
- **Whole student body shipped to browsers**: `teacher-dashboard:315-316`, `teacher-students:104-105`, `admin-dashboard:67,81,96,119,120` (scans `users` **twice**), `admin/announcements:57`, `bulk-academic-update:73`, `usermanagement:67-70`.
- **`sessions/history` fetches every ended session ever**, then `.slice(0, limit)` in JS (`route.ts:20-33`) — the `?limit=` bounds the response, not the read.
- **Serial N+1 loops**: `attendance/end:98-105` (2N reads), `session/[id]:172-204` (N sequential transactions), `analytics/[subjectId]:73-121` (unbounded × unbounded), `bulk-onboard-students:55-271` (~5 sequential round trips per student, including SMTP, so one stall blocks the whole upload).
- **All composite indexes are undeclared** — no `firestore.indexes.json`, no `firebase.json`, no `.firebaserc`. 6 queries strictly require a composite index; ~22 more are multi-equality. Combined with §1.6, a missing index fails silently into a table scan.

## 9. Deployment problems

- **`render.yaml:8` pins `plan: free`** — the service sleeps when idle. The keep-alive workaround (`0f37a1f`–`4dc4140`) exists solely to fight this, and its GitHub workflow is hardcoded to a 5-day window in September 2026, becoming a permanent no-op after 20 Sep 2026.

## 13. Risks introduced by the proposed P0 changes

Read this before starting work.

| Proposed change | Risk | Mitigation |
|---|---|---|
| **P0.1 Teacher ID** | Switching to a transactional counter must be **seeded from the existing maximum per prefix**, or it restarts at 1 and collides with live IDs. The counter must be per-prefix (PM/AD/VT). | Seed from a one-time scan; keep existing IDs untouched; add the tests listed in the brief, including "existing IDs of mixed length". Note the *real* fix must also address the deterministic collision path — teacher deletion must delete the Auth user, or IDs must never be reused. |
| **P0.2 Socket auth** | Chat has a **dual write path** (`Chats.tsx:1244-1259`). Enforcing identity on the socket without updating the client handshake will silently fall back to `addDoc`, masking the change. Long-lived sockets outlive 1-hour tokens, so naive re-verification will disconnect users mid-lecture. | Ship client and server together; re-check authorization on each privileged event rather than only at connect; keep `join` authorization server-side. Tightening `cors.origin` may break any non-origin client. |
| **P0.3 Firestore rules** | The highest-risk change in the list. Tightening `users` will **break the many client screens that full-scan `users`** (admin dashboard, announcements name lookup, teacher dashboard/students, bulk-update). Those pages must move to server APIs or scoped queries **first**, or the app breaks for every role. Note the reverse risk too: `edit-profile` already writes `teachers/{uid}` in violation of current rules, so some paths are already failing silently. | Write the rules test suite **before** changing rules; migrate readers first, tighten second; test with all three role tokens. |
| **P0.4 Paid hosting** | Low risk, but removing the keep-alive must not remove the scheduler it now guards; and in-process schedulers will double-fire if the plan change enables more than one instance. | Move schedulers off in-process timers, or pin a single instance, before scaling. |
| **P0.5 Backups** | A backup taken *before* the rules and data-model fixes will restore a vulnerable schema. Restore rehearsal must target a scratch project, never production. | Rehearse restore into a separate project; document retention and the responsible role; never commit credentials. |
| **P0.6 Rules/indexes as code** | Deploying `firestore.indexes.json` generated from a *guess* can drop indexes that exist only in the console, which — per §1.6 — will not error but will silently degrade to table scans. | Export the current live index set first, commit that as the baseline, then diff. |
| **P0.7 Logging** | Sweeping `console.*` risks deleting the only diagnostics that exist. Several logs sit in credential and biometric paths, so a structured logger must redact rather than relay. | Replace incrementally by module; add explicit redaction for passwords, tokens, OTPs, and the 128-float face descriptors; never log `student_faces` payloads. |

**Two cross-cutting risks:**

1. **There are no tests and no CI gate.** Every change in this list is unverifiable except by manual testing. The rules test suite (P0.3) and the ID tests (P0.1) should land *before* the changes they cover, not after.
2. **Sequencing matters.** P0.3 depends on first migrating the client full-scans; P0.6 depends on capturing the live index set; P0.5 should precede any destructive migration. Doing P0.3 first, in isolation, will take the application down.

## 14. Addendum — second-pass findings

A third audit pass (feature completeness, operations, code quality) produced material findings not covered above. Two of its own claims were **wrong** and are corrected first.

### 14.0 Corrections to the second pass

| Claim | Verdict | Evidence |
|---|---|---|
| "No PDF generation exists anywhere" | **FALSE** | PDF export is real, implemented as browser print-to-PDF: `teacher-students/page.tsx:276-343` builds an HTML table, then `printWindow.print()` at `:342`. A grep for `window.print` misses it because the variable is named `printWindow`. The client manual's "CSV/PDF export" claim is accurate. |
| "No XSS sinks" (stated in §2 above) | **INCOMPLETE** | True for `dangerouslySetInnerHTML`/`eval`, but `openPdfPrint` interpolates student fields into `document.write` **unescaped** — `` `<td>${student.name}</td>` `` (`teacher-students/page.tsx:281-295`). A name containing markup is injected into the print window. Low severity (teacher-initiated popup, institution-controlled data) but it is a real injection path. |

### 14.1 The anti-proxy attendance guarantees are weaker than presented

This matters commercially, because anti-proxy attendance is the product's main differentiator. Each layer is weaker than assumed:

- **Face "liveness" is not anti-spoofing.** The server-side check is only that frames are not byte-identical — `FACE_FRAME_MIN_VARIATION = 0.0001` (`constants.ts:297`), enforced at `mark-face/route.ts:260-278`. **Blink detection is client-only** (`FaceCameraCapture.tsx:12-18`) and is therefore not a security control — a caller hitting the API directly never performs it. Two slightly different photos of a photo would pass.
- **Geofencing is disabled in production** (`render.yaml:23-24`) **and** the client silently falls back to **IP geolocation** when GPS is denied — `student-attendance/page.tsx:78-105` calls `https://ipapi.co/json/`. That is city-level accuracy (useless as a classroom geofence) and sends student IP addresses to an undeclared third party, which is a privacy disclosure issue in its own right. `allowedDistanceMeters` is also hardcoded to 30 (`attendance/start:296`), while the Settings UI text claims "the configured radius" (`admin/settings/page.tsx:213-217`) — no such setting exists.
- **Device trust is cosmetic.** `deviceId` is a client-generated `localStorage` random string (`attendanceService.ts:306-320`) which the client self-registers with **unlimited overwrite** (`register-device/route.ts:23-31`). Copying the string to another device defeats it.
- **The student QR is a static, unsigned payload** with no nonce and no session binding (`StudentQRDisplay.tsx:21-38`) — a screenshot is a permanent proxy-attendance token. The scanner additionally accepts a **free-text manual UID** (`QRScanner.tsx:17-36, 113-127`), so a teacher can mark anyone with no artifact at all.
- **WebAuthn is the one genuinely strong layer** — single-use, session-bound, TTL'd server-side challenges (`webauthn.ts:68-132`), persisted signature counter (`:161-190`), `requireUserVerification: true` (`mark/route.ts:185`). Caveat: `expectedOrigin`/`expectedRPID` are derived from the request's own `Origin`/`Host` headers (`webauthn.ts:22-58`), which a non-browser client controls.

**Net:** of four advertised layers, one (WebAuthn) is strong, one is off in production, and two are bypassable. The marketing claim should be scoped to passkey-verified attendance until the others are hardened.

### 14.2 The socket leaks class rosters to every connected client

Beyond §1.1, session start broadcasts **globally rather than to a room**:

```ts
// src/app/api/attendance/start/route.ts:327
getIO()?.emit("attendance-session-started", responseSession);
```

`responseSession` includes `enrolledStudentIds` — the UID of every student in the class — delivered to **every connected socket, including unauthenticated ones** (per §1.1, anyone can connect). `join_attendance_session` (`socket.ts:29-118`) likewise joins any `attendance_<id>` room and receives `attendance-recorded` events carrying student names, PRNs and GPS coordinates.

### 14.3 Plaintext passwords are returned in an API response and written to a CSV

`bulk-onboard-students/route.ts:236-249` returns **generated plaintext passwords in the JSON response body**; `admin/upload-students/page.tsx:87-127` then writes them to a downloadable `manual-credential-delivery.csv` with a `password` column (`:101`). The same password is also emailed (`:216`). `.gitignore:14` anticipates this risk for `rotated-credentials-*.csv` but **does not cover this filename**.

### 14.4 Configuration and deployment issues

- **A fork or misconfigured staging deploy silently writes to the production Firebase project.** `src/lib/client/firebase.ts:18-34` hardcodes fallbacks for all six `NEXT_PUBLIC_FIREBASE_*` values, including `projectId: ... || "campusconnect-38759"`. Missing env vars produce a *working* app pointed at production rather than a loud failure.
- **No `.dockerignore` exists**, while `service-account-key.json` (populated, 2,397 bytes) and `.env.local` sit on disk at the repo root. Any `docker build`, `npm pack`, or folder zip carries them out. Git hygiene is correct (§2); filesystem hygiene is not.
- **Production runs TypeScript through `tsx` at runtime** — `npm start` is `cross-env NODE_ENV=production tsx server.ts` — not a compiled artifact.
- **Socket.IO uses the default in-memory adapter** (`server.ts:32-36`); there is no Redis adapter, so scaling past one instance silently breaks chat rooms and live attendance in addition to the join-map issue (§9).
- **Gemini env vars are absent from `render.yaml` entirely** (`GEMINI_API_KEY`, `GEMINI_MODEL`, `GEMINI_EXAM_MODEL`), so AI-assisted OCR structuring only works if an admin pastes a key per request. Relatedly, the **client may supply the Gemini key** via an `x-gemini-api-key` header or `geminiApiKey` body field (`gemini.ts:58-73`).
- **OCR and PDF parsing have no timeout and no `maxDuration`**, run server-side in the **same single process** that serves every page and every socket connection. A 10 MB scanned timetable blocks the event loop through a Tesseract pass while chat and live attendance stall.
- **README drift:** README says build `npm ci && npm run build` and health check `/api/subjects`; actual is `npm ci --include=dev && npm run build` and `/api/health` (`render.yaml:6-8`).
- **`.env.example` drift:** `GEMINI_MODEL=gemini-1.5-flash` documented vs `gemini-2.0-flash` in code (`gemini.ts:15`); `NEXT_PUBLIC_FACE_API_MODEL_URL`, all five `KEEP_ALIVE_*`, and `VITE_GEMINI_API_KEY` are undocumented. `gemini.ts:69` still reads `VITE_GEMINI_API_KEY` — a Vite-era name that can never be populated in Next.js.

### 14.5 Error-message leakage is systemic, not isolated

**38 of 56 API route files** return raw exception text to the client. `auth/verify-admin/route.ts:17-19` leaks the **entire error object**:

```ts
return NextResponse.json({ message: "Invalid token", error }, { status: 401 });
```

`attendanceService.ts:42-47` surfaces `data.message` straight into a `toast.error`, so Firestore internals reach the end user's screen.
